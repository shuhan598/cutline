# 切线算法与数据问题清单

> 更新时间：2026-08-02
>
> 本文档记录当前代码、数据契约、接口对接和上线闭环中仍需处理的问题。旧版文档中“溢满 / 切回 / 丝网 / 混料 / 逐台选取未实现”的结论已经过期：当前主链路已包含这些模块，并已通过自动化测试覆盖。

## 当前结论

当前正式调用链为：

```text
CutlineAlgorithmRequest
  -> SnapshotAdapter.to_algorithm_snapshot
  -> CutlinePipeline.evaluate_algorithm
  -> AlgorithmResponseMapper.to_evaluate_response
  -> CutlineEvaluateResponse
       = CutlineAlgorithmResponse 原业务字段 + persistence_state
```

算法已具备以下能力：

- 后端请求模型校验与快照转换。
- 机台状态标准化：后端“运行”/`running` 进入算法统一为 `running`，其它状态统一视为非运行。
- Buffer 区间净消耗速率计算。
- 断料预测、断料预警。
- 溢满预测、溢满预警。
- 断料/溢满候选机台筛选。
- 逐台影响校验和切线方案生成。
- 人工介入结果输出。
- Pending 跨轮确认、真实活动切线事件生成与切回判断。
- 丝网当前订单完工与清台准备提醒。
- 仅由真实 Active 触发的单次混料追溯及失败重试。
- 基础响应 `CutlineAlgorithmResponse` 与增强响应 `CutlineEvaluateResponse`。
- 完整假数据样例：`examples/backend_request_stockout_plan_sample.json`。
- 首轮/确认轮/切回轮增强响应样例：`examples/cutline_evaluate_*_response.json`。

## P1. 正式 HTTP 接口已实现

当前服务层入口为：

```python
CutlineService().evaluate_algorithm(request)
```

正式 HTTP 路由为：

```http
POST /cutline/evaluate
Content-Type: application/json
```

请求体使用 `CutlineAlgorithmRequest`，响应体使用增强的 `CutlineEvaluateResponse`。
`POST /stub/algo/run` 继续按基础 `CutlineAlgorithmResponse` 投影，不输出持久化状态。

## P2. 真实后端数据尚未联调

当前已有完整假数据样例，但还需要使用甲方真实接口数据验证以下内容：

- 顶层数据集是否齐全。
- 字段名是否完全匹配 `CutlineAlgorithmRequest`。
- 机台状态枚举是否只需支持“运行”/`running` 作为正常状态。
- 产品型号名称 `product_name` 是否非空且全局唯一。
- Buffer 与工序路线是否能唯一推导相邻工序关系。
- 库存订单是否能通过 `bound_source_name` 精确匹配唯一订单的产品型号名称。
- 机台、产线、订单、产品、产能表之间的引用是否完整。
- `machine_process_times` 是否包含混料追溯需要的工艺时间。

风险：真实数据只要缺少关键引用，算法会按设计抛出校验或转换错误，无法进入完整计算。

## P3. 净速率口径需业务确认

当前代码中的净消耗速率按机台实时 30 分钟输入/输出数量折算小时速率：

```text
上游产出速率 = 上游运行机台 output_quantity_30m 之和 * 2
下游吞入速率 = 下游运行机台 input_quantity_30m 之和 * 2
净消耗速率 = 下游吞入速率 - 上游产出速率
```

这与部分设计文档中“运行机台按静态表实际产能计算有效产能”的口径不同。

需要业务确认：

- 净速率到底以实时 30 分钟数据为准，还是以静态表实际产能为准。
- 若实时数据异常或长时间不刷新，是否允许回退到静态产能。
- 当前 30 分钟数量乘 2 的小时化方式是否符合现场统计周期。

## P4. Pending/Active 协议已闭环，待后端落库联调

算法通过 `persistence_state` 输出下一轮所需的完整状态：

- `pending_cutline_plans`
- `active_cutline_events`
- `expired_pending_plan_ids` / `completed_pending_plan_ids`
- `return_suggested_event_ids` / `mixed_cutline_event_ids`
- `new_mixing_trace_records`

基础业务字段仍按原结构返回，不与持久化状态混在一起。

后端需要完成：

1. 原子保存每轮完整 `persistence_state`。
2. 下轮把 Pending、Active 和两个累计 ID 水位映射回请求同名字段。
3. 不根据公开 `event_id` 反向解析方案，也不自行推导确认状态。
4. 保存 Active 的 `status`、`warning_id` 等完整上下文。
5. 对现场已完成、已取消或已切回的事件做生命周期管理。

如果后端不保存该状态，Pending 确认、混料和切回防重都会丢失跨轮上下文。

## P6. 部分业务规则未定版

仍需业务或现场确认的规则包括：

- 片源兼容规则：例如 `A-`、`A` 的优先级，以及“A 不能切到 A”是否成立。
- S2 车间 R/P 共用机台特例的适用范围。
- 丝网前 R/P 是否始终视为兼容。
- 切线方案是否允许同 Buffer 内切换。
- 溢满场景下目标订单选择优先级。
- 多个预警同时触发时的最终排序策略是否符合现场调度习惯。

## P7. MES 混料推送闭环未实现

当前算法可以生成 `mixing_trace_records`，但不会主动推送 MES，也不会写数据库。

后续系统集成需要明确：

- 后端是否保存混料记录。
- 由后端还是算法服务推送 MES。
- MES 接口格式。
- 推送失败后的重试策略。
- `notification_status=scheduled/due` 的状态更新方式。

## P8. 生产级日志、监控和错误码不足

当前响应中已有 `errors`，但生产运行还需要更完整的工程能力：

- 每次请求的 `run_id` 贯穿日志。
- 结构化日志。
- 统一接口错误码。
- Schema 校验错误与算法局部错误分层。
- 关键指标监控：请求量、失败率、预警数量、方案数量、人工介入数量。
- 慢请求和异常告警。

## P10. 本地环境 `.pytest_cache` 权限警告

当前运行 Git 或 pytest 时，本地 `.pytest_cache` 目录可能出现权限警告：

```text
warning: could not open directory '.pytest_cache/': Permission denied
```

该问题不影响算法代码和测试结果，但会影响本地状态查看体验。建议后续清理本地缓存目录权限。
