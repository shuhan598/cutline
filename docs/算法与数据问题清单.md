## 🔴 严重级（必须先解决，否则甲方数据接入即失效）

### P1. Schema 与算法/示例数据字段名完全对不上

`app/schemas/common_schema.py` 用 Pydantic 定义的字段，**算法层一个都没用到**。算法直接读原始 dict，且读的是另一套字段名。若甲方按 schema 给数据，算法会把这些字段全部读成 `None`/`0`，**一条预警都不会触发**。

| 概念 | 算法 + 示例 JSON 实际读取 | schema 定义 | 后果 |
|---|---|---|---|
| 库存量 | `inventory_quantity` | `currentStockQuantity` | 读不到 → 库存=0 |
| 区间工序 | `process_from` / `process_to` | `source_process_code` / `target_process_code` | 读不到 → 机台匹配不上 |
| 机台速率 | `input_rate_per_hour` / `output_rate_per_hour` | `input_rate` / `output_rate` | 读不到 → 净速率=0 |
| 机台产能 | `actual_capacity_per_hour` | `actual_capacity` | 读不到 |
| 静态产能 | `actual_capacity_per_hour` / `theoretical_uph` | `actual_capacity` / `rated_capacity` | 读不到 |

**处理建议**：与甲方确认字段清单，定一套 canonical（标准）字段契约，让 schema、示例数据、算法三处统一。当前 schema 等同于"装饰品"。

### P2. 机台 `process_code` 拆表后无 join 逻辑

`MachineRuntimeStatus`（实时状态）里**没有 `process_code`**，被拆到了 `MachineMaster`（主数据）。但算法是直接从机台 dict 上读 `process_code`，**没有按 `equipment_code` 把两张表关联起来的逻辑**。

- 影响文件：`app/core/net_rate/net_rate_calculator.py`、`app/core/candidate_machine/candidate_machine_finder.py`
- 后果：若甲方按 schema 分表给数据，所有机台的 `process_code` 读为 `None`，工序匹配全部失败。
- **处理建议**：要么数据层把 `process_code` 合并进实时状态，要么算法层增加 master/runtime 的 join。

## 🟠 数据规范问题

### P3. 两份示例数据字段集不一致
- `examples/cutline_sample_input.json`：字段丰富甚至冗余（机台带 `wafer_size`/`shape_code`/`theoretical_uph`、`input_quantity_30min` 等）。
- `examples/cutline_complex_input.json`：极简（机台仅 6 字段，无产能、无尺寸）。
- 甲方真实数据只会是一种格式。**建议确定一份作为标准模板**。

### P4. `buffer_inventories` 同时带两套工序字段
`sample` 数据里每条库存同时有 `source_process_code`+`target_process_code` 和 `process_from`+`process_to`，说明字段尚未定型。**挑一套保留**。

### P5. 命名风格不统一
`currentStockQuantity` 为 camelCase，项目其余字段均为 snake_case。统一为 snake_case。

## 🟡 算法逻辑问题

### P6. 净速率口径与设计文档冲突
- 代码取**实时速率** `input_rate_per_hour`（fallback：实时速率 → 半小时量×2 → 静态产能），来源 `app/core/net_rate/rate_utils.py`。
- 但设计文档 v2 第 2.2 节规定有效产能应取**静态表7的实际产能**。
- **需与甲方确认**：是否提供实时速率字段。若仅给静态产能，则当前 fallback 链需重新设计。

### P7. 库存去重口径不一致
- `net_rate` 用 `seen_segments` 对区间去重（`net_rate_calculator.py`）。
- `depletion` 的 `find_inventory_quantity` 对库存行**累加且不去重**（`depletion_time_calculator.py:28-36`）。
- 若甲方数据存在重复库存行，两处会算出互相矛盾的结果。需统一去重策略。

### P8. 候选机台输出未携带产能 —— 阻塞 3.3
- `candidate_machine_finder.py:69-80` 生成的候选 dict 只含尺寸/形状/型号，**无 `actual_capacity`**。
- 设计文档 3.3 的"切几台 / 按缺口匹配 / 借出影响校验 / 切入量计算"全部依赖每台的实际产能。
- 同时 `complex` 示例数据本身缺产能表（`capacity_records`）。
- **处理建议**：候选结果必须带上产能字段，且数据层需补齐每台每型号的静态产能。

### P9. 未实现 S2 车间 R/P 共用机台特例
`is_same_size_and_shape` 要求形状代码严格相等；设计文档 3.2 规定丝网工序之前 R 与 P 视为同形状。暂可接受，需登记待办。

### P10. 死分支 reason 描述误导（小）
`find_candidates_for_warning` 中"未触发预警"分支返回 `reason="no_compatible_running_upstream_machine"`，但该分支已被 `find_all_candidates` 预过滤，属死代码，描述与实际不符。
