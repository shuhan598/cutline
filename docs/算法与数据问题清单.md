## 🔴 严重级（必须先解决，否则甲方数据接入即失效）

### P1. Schema 与算法/示例数据字段名完全对不上 ✅ 已修复（2026-06-18 彻底落地）

> 修复前：`app/schemas/common_schema.py` 用 Pydantic 定义的字段算法层一个都没用到，算法直接读原始 dict 且读另一套字段名，schema 等同于"装饰品"。
> 修复后：schema 即唯一字段契约，`common_schema.py` 已采用下表"算法侧"的 snake_case 字段名；`SnapshotAdapter` 把 dict→`CutlineSnapshot`，四个算法组件全部读对象（`snapshot.machine_statuses`、`inventory.inventory_quantity`、`snapshot.config.cutline_lead_minutes`），不再触碰 dict。

下表为修复前的三方错位，现已通过统一字段名消除（保留备查）：

| 概念 | 算法/示例字段（现 canonical） | 旧 schema 字段（已废弃） | 修复前后果 |
|---|---|---|---|
| 库存量 | `inventory_quantity` | `currentStockQuantity` | 读不到 → 库存=0 |
| 区间工序 | `process_from` / `process_to` | `source_process_code` / `target_process_code` | 读不到 → 机台匹配不上 |
| 机台速率 | `input_rate_per_hour` / `output_rate_per_hour` | `input_rate` / `output_rate` | 读不到 → 净速率=0 |
| 机台产能 | `actual_capacity_per_hour` | `actual_capacity` | 读不到 |
| 静态产能 | `actual_capacity_per_hour` / `theoretical_uph` | `actual_capacity` / `rated_capacity` | 读不到 |

**遗留**：canonical 字段契约已统一（以算法/示例字段名为准）并接入算法；仍需与甲方真实数据最终核对字段清单。

### P2. 机台 `process_code` 拆表后无 join 逻辑 ✅ 已修复

> 修复后：`process_code` 已合并进 `MachineRuntimeStatus`（`common_schema.py`），算法直接读 `machine.process_code`，无需 master/runtime join。

- 原问题：`MachineRuntimeStatus`（实时状态）曾无 `process_code`（被拆到 `MachineMaster` 主数据），算法直接从机台读 `process_code` 又无按 `equipment_code` 关联两表的逻辑；甲方若按 schema 分表给数据，工序匹配会全部失败。
- 影响文件：`app/core/net_rate/net_rate_calculator.py`、`app/core/candidate_machine/candidate_machine_finder.py`

### P3. 两份示例数据字段集不一致
- `examples/cutline_sample_input.json`：字段丰富甚至冗余（机台带 `wafer_size`/`shape_code`/`theoretical_uph`、`input_quantity_30min` 等）。

### P4. `buffer_inventories` 同时带两套工序字段
`sample` 数据里每条库存同时有 `source_process_code`+`target_process_code` 和 `process_from`+`process_to`，说明字段尚未定型。**挑一套保留**。

### P5. 命名风格不统一
`currentStockQuantity` 为 camelCase，项目其余字段均为 snake_case。统一为 snake_case。

## 🟡 算法逻辑问题

### P6. 净速率口径与设计文档冲突
- 代码取**实时速率** `input_rate_per_hour`（fallback：实时速率 → 近30min量×2 → 静态产能 → 0），现已显式化为 `app/core/net_rate/rate_strategy.py` 的 `RealtimeFirstRateStrategy`（原 `rate_utils.py` 已删除）。
- 但设计文档 v2 第 2.2 节规定有效产能应取**静态表7的实际产能**。
- **需与甲方确认**：是否提供实时速率字段。若仅给静态产能，则当前 fallback 链需重新设计。

### P7. 库存去重口径不一致
- `net_rate` 用 `seen_segments` 对区间去重（`net_rate_calculator.py`）。
- `depletion` 的 `_inventory_quantity` 对库存行**累加且不去重**（`depletion_time_calculator.py` 第 52-69 行）。
- 若甲方数据存在重复库存行，两处会算出互相矛盾的结果。需统一去重策略。

### P8. 候选机台输出未携带产能 —— 阻塞 3.3 ✅ 已修复
> 修复后：`CandidateMachineFinder` 产出的 `CandidateMachine` 已带 `contribution_capacity_per_hour`（取自 `snapshot.capacity_records`，缺记录时为 `None`），门面再映射为 `SelectedMachine.contribution_capacity`。
- 设计文档 3.3 的"切几台 / 按缺口匹配 / 借出影响校验 / 切入量计算"全部依赖每台的实际产能——产能字段已就位，逐台选取逻辑仍待实现。
- **遗留**：`complex` 示例数据本身缺产能表（`capacity_records`），此时候选产能为 `None`，需数据层补齐每台每型号的静态产能。

### P9. 未实现 S2 车间 R/P 共用机台特例
`is_same_size_and_shape` 要求形状代码严格相等；设计文档 3.2 规定丝网工序之前 R 与 P 视为同形状。暂可接受，需登记待办。

### P10. 死分支 reason 描述误导（小）✅ 已修复
重构后 `CandidateMachineFinder._for_warning` 只接收已触发预警（在 `find` 内预过滤），`reason="no_compatible_running_upstream_machine"` 现用于"有预警但无合规候选机台"这一可达分支（`candidate_status="manual_intervention_required"`），死代码已消除。
